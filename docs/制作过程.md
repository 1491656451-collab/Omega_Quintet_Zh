# 《欧米伽五重奏》汉化制作全过程复盘

写给想自己动手的人。日期：2026-09-18

这份东西不是流程清单，是**思路复盘** —— 每一步为什么这么走、当时有哪些岔路、
我在哪里判断错了又是怎么发现的。做完这一个游戏，我觉得可复用的东西主要是**方法**，
而不是那些具体的偏移量。

---

# 零、先把这件事的骨架看清

给一个商业游戏做汉化，本质上是三层嵌套的解包问题：

```
容器层    .bra 归档  →  怎么拆开、怎么装回去
结构层    归档里的文件格式（表格 / 字符串池 / UI 容器 / 贴图 / 字体）
内容层    真正要翻的那些字
```

**大部分人卡在结构层**，而不是内容层。翻译本身是最不费脑子的部分。
这个项目 19 轮里，真正花在「想中文怎么说」上的时间大概占两成，
剩下八成是：这段字在哪、怎么写回去不崩、写回去之后屏幕上是不是真变了。

还有一条贯穿全程的判断线：

> **屏幕上的每一个字，要么来自数据文件，要么来自可执行文件，要么根本不是字（是贴图）。**

这三条路的处理难度差着量级：数据文件最好办，贴图很麻烦但能做，
exe 里的（带反篡改校验时）做不了。所以**每次遇到一句没翻的，第一件事是判断它属于哪一类**，
而不是急着去找。这条判断线我前期没有自觉，吃了好几次亏，后面会讲。

# 一、容器层：把 .bra 拆开

游戏目录里 10 个 `.bra`，从 30MB 到 740MB，总共 2.7GB，54,534 个成员。

## 1.1 怎么逆一个未知归档格式

拿十六进制看文件头，第一眼就有东西：

```
50 44 41 00   "PDA\0"      magic
xx xx xx xx   版本
xx xx xx xx   一个很大的偏移 —— 接近文件尾部
xx xx xx xx   一个几百到几万的数 —— 像是成员数
```

「一个指向文件尾部的偏移 + 一个像计数的数」= **索引在文件末尾**。
这是归档格式最常见的布局（zip 也是这样）。跳到那个偏移，果然是一串等长记录。

索引项的结构靠**对齐猜 + 交叉验证**推出来：

```python
# 索引项：<IIIIHHI> + 变长文件名
h1, h2, csz, usz = unpack('<IIII', d, p)      # csz 压缩后大小，usz 原始大小
nl, flg          = unpack('<HH',   d, p+16)   # nl 文件名长度，flg 标志
off,             = unpack('<I',    d, p+20)   # off 数据块在文件里的偏移
name             = d[p+24 : p+24+nl]
p += 24 + nl
```

**怎么确认猜对了**：`usz > csz` 而且 `off` 单调递增、相邻 off 之差正好等于 `csz` ——
三个独立的一致性条件同时成立，就不可能是巧合了。这比「看着像」可靠得多。

每个成员的数据块前面还有 16 字节自己的块头：

```python
usz, csz, ts, flg, pad = unpack('<IIIHH', d, off)   # flg==6 → 裸 deflate
blob = d[off+16 : off+16+csz]
raw  = zlib.decompress(blob, -15)                   # -15 = 裸流，没有 zlib 头
```

**这里有个坑，我栽过**：索引里的 `csz` **含**那 16 字节块头，块头里的 `csz` **不含**。
差 16 字节，解压会报 `invalid distance too far back` 那种莫名其妙的错。
逆格式时遇到「差一个固定小常数」的错，先怀疑「某个长度字段包不包含头」。

`zlib.decompress(blob, -15)` 里的 `-15` 也值得说：正数 wbits 是带 zlib 头的流，
`-15` 是**裸 deflate**（raw deflate），游戏归档里基本都用裸流省 6 个字节。
写回去也要用 `zlib.compressobj(9, zlib.DEFLATED, -15)`，不是 `zlib.compress()`。

## 1.2 从一开始就写「回读比对」

拆开之后**立刻**写一个反向操作：重新打包，然后逐成员解压出来和原始比。

```python
assert repack(src, {}) 的每个成员 == 原包的每个成员
```

这一步不产出任何东西，纯粹是给自己立一道底线。后面每一次改包都靠它兜着。
**不要等到出问题才补测试** —— 逆向工程里，「以为改对了其实改错了」是最贵的错误，
因为它不会立刻报错，而是在你实机跑到第 30 小时的时候黑屏。

# 二、结构层：四种文件格式

拆开之后，成员名就把地图画出来了：

```
database\ database_en\ database_kr\    ← 日 / 英 / 韩三套数据
  database.cl3      一个容器，里面 45 张表
  strMenu.gstr      菜单文本
  strSystem.gstr    系统文本
  strRpg.gstr       战斗/RPG 文本
  strEvent.gstr     剧情文本
window\font\sysfont.ffu  advfont.ffu   ← 两个字体
global\Texture\grSystem*.dds           ← UI 贴图
```

## 2.1 `.gstr`（GSTL）—— 最简单的一种

magic `GSTL`，里面是 `[id, key, 字符串]` 三元组。**按 id 索引**。

这个「按 id 索引」的性质决定了一件关键的事：

> **日 / 英 / 韩三套的 id 是对得上的 → 三套必须一起换。**

为什么必须？因为 PC 移植版有时会去读别的 locale 那一份（比如判断某条是否为空）。
只换英文那套，个别地方会漏出日文。这条是实机试出来的，不是推出来的。

## 2.2 `.cl3`（CL3L）—— UI 容器

```
0x00  magic 'CL3L'
0x38  段描述符区，每段 0x50 字节
        名字(32B) + cnt + size + tbl     ← tbl 在 +40，不是 +44
      最后一段叫 FILE_LINK，读到它就停
FILE_COLLECTION 段的 tbl 指向条目表：
      每条 560 字节
        +0    名字（最长 256）
        +516  数据偏移（**相对 tbl**，不是相对文件头）
        +520  数据大小
```

**两个坑**：

1. `tbl` 字段在 `+40`。我一开始按 `+44` 读，拿到的全是垃圾。
   怎么发现的：写了个 `cl3w.selftest()`，把容器拆开再原样装回，
   要求**字节级一致**。`+44` 过不了这道自检，`+40` 过。
   **逆向里的偏移量不要靠猜，靠「哪个值能让往返一致」来定。**
2. 成员布局是**连续无填充**的，而且每个 `size` 都是 16 的倍数。
   往回写的时候必须保持这两条，否则游戏读到一半就崩。

## 2.3 GBNL —— 数据库表，最有意思的一个

`database.cl3` 里那 45 张表（`stItem` `stSkill` `stCharaMonster`…）都是这个格式。
它的 magic 在**文件末尾往前 64 字节**，不在开头 —— 这种设计一开始很容易看漏：

```
[ 行记录区 ][ 列描述区 ][ 字符串池 ][ 64 字节尾部，magic 'GBNL' ]
```

尾部那 64 字节里有 12 个 u32：行数、行长、列数、行区总长、字符串数、字符串池偏移……
读到这些，整张表就全通了。

**列描述**是 `u16 类型 + u16 偏移` 的数组。类型 5 = 「这一列存的是字符串池里的偏移」。
于是取文本变成：

```python
rel = unpack('<I', raw, row*rowsize + col_offset)   # 行里存的是相对偏移
s   = raw[pool+rel : raw.index(b'\0', pool+rel)]    # 池子里 NUL 结尾
```

### 这里是我整个项目最大的一次判断失误

按上面这套，我导出了 8396 条说明文，翻完回填，实机一看：**说明文全是中文，
但道具名、技能名、怪物名、迷宫名全是英文。** 2000 多条名称一条都没动。

原因：**名称不是类型 5 的池字符串，而是行记录里的定长内嵌字段。**

```
列描述里长这样：  (1, 12)  ... 下一列 (0, 76)
                   ↑type    ↑offset      两者相差 64
```

类型 1 通常是「1 字节的小整数」，但**当类型 1 的列和下一列之间隔着 64 字节**时，
它就不是整数，而是一个 64 字节的定长字符串字段，字符串直接躺在行记录里。

**教训（这条最值钱）**：

> 探针只查了你以为存在的那一种存法，就等于没查。
> 判断「某张表里的文本是否全部找到」，要拿**列描述表的总跨度**去核账 ——
> 每列的 offset 到下一列的 offset 之间有多少字节、这些字节被哪种类型解释了。
> 有跨度没人认领 = 你漏了一种存法。

后来写了个小工具把七张表的名称字段位置全推出来（`stItem +0x0c/64`、
`stSkill +0x08/64`、`stMaterial +0x04/32`…），一次补齐 1869 条。

### 空重建闸 —— 整个项目最关键的一道自检

改 GBNL 要重建字符串池（因为中文长度和英文不一样）。重建是有风险的：
原始文件里可能有你没理解的东西（重复字符串共享、特定的对齐填充、尾部垃圾字节）。

所以每张表在改之前先跑这一句：

```python
assert g.rebuild({}) == raw        # 什么都不改地重建，必须字节一致
```

**45 张表里只有 25 张能过。** 过不了的（`stDungeon` `stMaterial`）说明我对那张表的
理解还有缺口 —— 这时候正确的做法**不是硬上**，而是**换一条更保守的路**：
只在原地覆写行记录里的定长字段，完全不碰字符串池。

> 逆向工程里，「我理解得不够」和「我能不能完成任务」是两个问题。
> 空重建闸的价值就是把这两件事分开：过不了闸的表，走一条不需要完整理解的窄路。

### 还有一条：`database.cl3` 和 `.gstr` 的处理**正好相反**

| | 索引方式 | 三套 locale |
|---|---|---|
| `.gstr` | 按 id | **必须三套一起换** |
| `database.cl3` | 按行号 | **只能换 `database_en\`** |

因为日/韩版的 `database.cl3` 是 6952 行，英文版是 7059 行 —— **行数不同，行号对不上**。
往日文那份里按英文的行号写，会把内容错位塞到别的道具上。

同一个包里两种文件，处理策略完全相反。**不要总结出「这个游戏的文本都怎么改」这种规律，
要一个格式一个格式地问「它靠什么索引」。**

## 2.4 字体：缺字是第一道硬墙

翻译回填完，实机一看满屏豆腐块。游戏自带的字体是日文版的，
包含日文汉字，但**简体中文有大量字它没有**（「维」「设」「图」这些简化字）。

字体格式 `.ffu` 是这个引擎自己的位图字体容器：一张字形图集 + 一张码位→格子的映射表。
处理办法：

1. 把原字体的映射表读出来，知道哪些码位已有；
2. 用 Noto Sans CJK SC Black 渲染缺的那些字形（最后一共补了 **20,924 个 CJK 字形**）；
3. 追加到图集里，映射表加对应条目。

体积代价：`sysfont` 8.6MB → 16.1MB，`advfont` 15.1MB → 33.5MB。
这也是后来做差分补丁时，字体那两项塞不回原槽位、必须支持「追加写」的原因。

**顺序上的经验**：字体要**第一轮就做**，和第一批文本一起验。
否则你分不清「屏幕上不对」是翻译错了还是字体缺字。
第 1 轮我只做了 410 条菜单 + 字体，就是为了用最小的量把这条链路走通。

# 三、找不到的字怎么办 —— 三条路的判断

前面说了，屏幕上的字有三个来源。**搜不到的时候怎么定性**，是这个项目里我提炼出的
最有用的一套判断：

## 3.1 全文搜索要搜到什么程度才算「搜过了」

不是 `grep`。必须：

- **10 个 .bra 全部逐成员解压**（54,534 个成员，解压失败必须是 0 ——
  有失败就说明你的解析有漏洞，不能宣称搜过了）；
- **三种编码**：UTF-8 / UTF-16LE / CP932（日文游戏很可能是 Shift-JIS）；
- exe 也搜，而且 exe 要按**节（section）**分开看，`.text` 里的命中大概率是代码字节的巧合。

我写的 `scan_itemname.py` 就是干这个的，2.7GB 跑完不到一分钟
（解压是瓶颈，但顺序读 + 逐成员解压很快）。

## 3.2 搜得到 vs 搜不到，含义完全不同

| 情况 | 结论 |
|---|---|
| 搜得到，改了屏幕上也变了 | 正常，收工 |
| **搜得到，改了屏幕上没变** | 有另一份顶替它 —— **去 exe 里搜这句的改写版** |
| **完全搜不到** | 要么是贴图，要么写死在 exe 里 |

第二种最阴，举个实例：教程提示里那五句 `※Or by pressing 〔Q〕 during battle.`，
在 `strEvent 7206~7212` 里有，我也译了，但屏幕上还是英文。

原因：主机版那五句写的是「触摸板左侧」，PC 移植版要显示键盘按键图标，
**在 exe 里另写了一份顶替掉数据里那份**。所以教程框里会出现「上一行中文、下一行英文」。

> **搜得到但没生效 → 去 exe 里搜同义的改写版。** 这条规则后来又命中一次：
> 设置里 `strSystem 523` 我们译了「战斗：位置记忆」，屏幕上显示 `Last Skill Used` ——
> PC 移植版把这个设置项整个换掉了。

## 3.3 第三种：是贴图

`Support Rate` / `Play Time` / 战斗指令表 / 地图图例 —— 这些在所有数据文件里都搜不到，
因为它们**根本不是字符串，是画在贴图上的美术字**。

**这是我第二大失误的来源**：前 5 轮我以为贴图都做完了，
其实 `grSystemBattle.dds`（整个战斗 HUD，61 处标签）一直没碰，到第 15 轮才发现。
而且第 19 轮又发现两张漏的（`Sprites.dds` 的设置页签、`grSystemWindow.dds`）。

**为什么会漏**：我按名字猜。看到 `grSystem*.dds` 一批就以为是全部，
而 `Sprites.dds` `Keyboard.dds` `Letterbox.dds` 这些 PC 移植版新加的名字没进视野。

> **正确做法：把包里所有 `.dds` 全部解码，拼成一张 contact sheet，肉眼扫一遍。**
> 30 张图拼成一张，看一眼就知道哪张有字。这件事十分钟，我却拖了 19 轮。
> 同理，做单张贴图时**先看整图 overview，别只扫一个区域** ——
> `grSystemMenuMain` 我第 8 轮只扫了 y≥830 那一条，上面的东西全漏了。

# 四、贴图汉化：整个项目技术含量最高的部分

这部分我写了大约 2000 行代码，踩的坑最多，也最值得讲。

## 4.1 基本约束：UV 包含

游戏不是「显示一张图」，而是**从图集里按固定的 UV 矩形取一小块画到屏幕上**。
所以有一条铁律：

> **中文的墨迹一个像素都不能画出这个标签自己的框。**
> 越界的部分会跑到相邻标签的画面上去。

推论（这条区分很重要）：

- **擦除矩形可以比框大**（多擦一点没关系，那块反正是透明/底板）
- **落笔矩形绝不可以**（画出去就串台）

出包前必须跑溢出检查：算出改动过的像素集合，逐个确认落在自己的允许框里。
我的 `checkbleed.py` 干这个，输出「战斗图 42 个像素、结算 7 个」这种数字 ——
零星几个点是抗锯齿边缘，只要没砸到**未替换**的框上就行。

## 4.2 怎么把原文擦干净 —— 三种确定性擦法

**第一版我用了通用的 inpaint（图像修复）算法，结果是灾难**：
Character Switch、Request、Magnetic Field 那几块的底板全被抹成一团糊。

原因很好理解：inpaint 是为照片设计的，它会「编」内容。
而 UI 底板是**规则的**（横向连续的光条、渐变色带），编出来的东西一眼假。

改成三种**确定性**的擦法，按底板的性质选：

| 擦法 | 适用 | 做法 |
|---|---|---|
| `clear` | 底本来是透明的 | 矩形清零，最简单 |
| `rows` | 底板横向连续（光条、色带） | **只填文字掩膜标中的像素**，逐行在缺口左右做线性插值。**首选** |
| `prof` | 文字几乎占满整条，没有干净的参照行 | 底板 = 竖直剖面 v(y) + 横向剖面 h(x) 分离重建：`fill(y,x) = v(y) + (h(x) − h̄)` |

`rows` 为什么是首选：它**只动文字占的那些像素**，底板上没被字盖住的地方一个字节不改。
这比「整块重建」保守得多，出错的面积天然受限。

### 三条血泪教训

**（1）绝不要「从紧邻的一列插值」。**

我一开始取缺口左右各 1 列来插值，结果指令条上出现了一条白色药丸状的横带。
因为紧邻那一列很容易落在**文字的外发光**上 —— 一个脏像素会被线性插值拉成一整条。

正确做法：插值的锚点要取**离墨迹足够远的干净列块**（取中位数，抗噪），
或者用掩膜把发光也算进「要填的区域」。

**（2）文字掩膜会把光条自己的高光线当成字。**

光条上有一条贯穿的亮线，亮度和文字接近，掩膜一做就把它标成文字，
擦完光条上多一道缺口。

规则：**整行都命中的行是底板不是字** —— 一行里覆盖率 > 85% 的，从掩膜里剔掉。
而且要**膨胀前剔一次、膨胀后再剔一次**（膨胀会把它重新连回来）。

**（3）`scipy.ndimage.binary_dilation(..., iterations=0)` 不是「不膨胀」，
是「膨胀到不再变化」。**

写成 0 会把整个矩形填满，擦除范围直接失控。要 `if it > 0: dilate(...)`。
这种 API 语义陷阱，只能靠「结果看着不对就去读文档」发现。

**（4）擦除框的边要离原文墨迹留 4~6 像素。**

`Support Rate` 那次，擦除框的左边缘正好压在 `S` 的竖笔上，
留下一条白边。因为掩膜的首尾列是插值锚点，会被强制保留。

## 4.3 样式：从原像素采样，不要手写

每个标签的颜色、描边、外发光都不一样。手写样式表在第 5 轮就崩了（318 个标签）。

改成从原像素**采样**：

```
核心 = 实心区(alpha>200) 腐蚀 2 次        → 避开描边，得到填充色
  再按亮度去掉最暗的 22%                   → 那些是抗锯齿过渡像素，会把颜色拉暗
填充色按 y 做线性拟合                     → 得到顶色 / 底色（UI 字多是竖直渐变）
描边 = 实心区 − 核心膨胀后                 → 得到描边色和描边宽度 ew
外发光 = 实心区外圈的色相                   → 得到发光色和半径
```

**一个容易忽略的细节**：采样必须**只用文字掩膜内的像素**。
我在 platefix 里一开始沿用了通用的 `alpha>200` 采样，结果在光条上采到的是**底板颜色**，
渲染出来的中文是光条色的，几乎看不见。

## 4.4 字号：CJK 要对齐英文的「字身高」，不是框高

这是我第三次犯的错，也是最容易犯的。

`fit_size()` 只保证「塞得进框」。但框是按光条内高给的，而：

- 拉丁字母的墨迹里有**下伸部**（p、g、y），框高往往比字身（cap height）高一大截；
- **汉字没有下伸部，墨高 ≈ 字号。**

让 `fit_size` 按框高去顶，顶出来 31 号、墨高 33px，而英文的字身只有 17~18px ——
**中文字号差不多是英文的两倍**，撑出光条，难看得一眼就能看出来。

正确做法：

```
先量英文的字身高（去掉下伸部那几行）→ 把字号定在那个数上下
字号 = 字身高 − 2 × 描边宽度            （描边是额外加出来的）
```

怎么量「去掉下伸部」：做行覆盖率剖面，**覆盖率跌到峰值 40% 以下的最后一行就是基线**，
跌下去那一小截是下伸部。

```
灰 Input 的剖面：
  y=158  10  #####          ← 'I' 和 'p' 的竖笔，cap top
  y=164  61  ############   ← x-height 开始，覆盖率跳升
  y=183  56  ############   ← 基线
  y=184  10  #####          ← 只剩 'p' 的下伸部
```

字身高 = 183 − 158 + 1 = 26px。

## 4.5 同一组标签必须同一个字号：`ONE_SIZE`

这是我**第四次**犯错，而且是「把用户的话理解反了」那种错，值得单独讲。

用户报「战斗指令表大小不一致」。我当成「金色比灰色大」，
于是把 24 条压成同一个字号 —— **结果把游戏原本就有的「选中项更大」这个设计抹掉了。**

用户纠正：「金色确实更大没问题，我的意思是**非金色字体有大小不一致**的问题。」

真正的根子在美术图：同一列标签的检测框高本来就在波动 ——

```
灰（未选中）：26 26 25 27 31 25 26 31 32 31 31 31   (px)
金（选中）  ：36 31 29 32 36 32 33 39 39 37 37 37
```

逐框算字号 → 框高一波动字号就跟着波动 → 同一列里条条大小不一。

解法：`ONE_SIZE = [[灰的框号...], [金的框号...]]`，**每组内部**取「各自能容下的最大字号」
里的**最小**那个。灰 12 条 → 21 号（墨高全部 23px），金 12 条 → 26 号（墨高 28px）。

> **教训**：用户说「不一致」时，先量清楚**是哪一组之间不一致**，别自己脑补。
> 我事后的做法是把三版（改前 / 理解错的那版 / 改对的那版）拼成一张对比图发过去，
> 让对方一眼确认 —— 这比文字描述省好几轮。

## 4.6 对齐：一列/一排标签要左对齐，不能居中

英文标签在图集里往往是**左边缘对齐**的（说明游戏按左边缘排）。
中文比英文短，如果在框里居中放，一列看过去就参差不齐。

怎么判断某处的偏移是不是居中造成的：

```
偏移量 = (英文墨宽 − 中文墨宽) / 2
```

拿用户截图上量出来的偏移（按缩放折算回贴图尺度）去对，对得上就是它。

「状态异常」那次就是这么定位的：同屏「状态」离◇ 22px、「状态异常」离◇ 72px，差 50px；
折算回贴图约 63px，而居中造成的偏移是 `(194 − 91)/2 = 51.5px` —— 对得上，就是它。

**但反过来也会错**：这次设置页签「图像 / 输入」我按左对齐做，用户说不居中。
因为那两个页签的底板是固定宽的，中文短了就显得偏左。改成居中才对。

> 左对齐还是居中，**取决于游戏怎么摆这个 quad，而这个信息通常读不到**
> （UV 矩形写在加密的 `.text` 里）。所以这一处只能做假设 + 实机验。
> 承认「这是假设」比假装有依据重要。

## 4.7 BC7 → BC3 的偷梁换柱

贴图是 BC7 压缩的（`dxgiFormat = 98`）。BC7 的编码器不好找，而 BC3（DXT5）遍地都是。

关键观察：**BC7 和 BC3 都是 16 字节 / 4×4 像素块**，所以同尺寸图的数据长度**一字节不差**。

于是：

```
texture2ddecoder.decode_bc7(...)  → 解成 RGBA
改图
quicktex 编 BC3                    → 长度完全相同
把 DDS 头里的 dxgiFormat 从 98 改成 77
```

体积不变 = 可以做原地补丁。画质有损失（明显差异像素 0.15%~2.3%，集中在抗锯齿边缘），
实机看不出来。

**一个藏得很深的坑**：这游戏的 `.dds` 成员**尾部还有 33 字节** ——
`\x0b` + `"NAME.tid"`。编码器不会生成它，忘了接回去，游戏加载那张图就崩。
（但不是每张都有，`Sprites.dds` 就没有 —— 所以要按
「`len(header) + 块数×16` 和实际长度的差」来判断，别写死。）

# 五、文本内容：怎么把一万多条翻得不出乱子

## 5.1 分批 + 三栏对照

11039 条剧情、8396 条说明文，不可能一口气过。分成 12 批，每批产出三栏对照
（原文 / 初译 / 润色）。三栏的意义是**留下可复核的痕迹** —— 出问题时能看出是哪一步引入的。

## 5.2 「白捡译文」的两个机制（省了几百条的工作量）

**（1）括号专名配对。**

已译的说明文里有大量 `Learn Mic Skill [Stecca Staccato]` 这种带方括号的专名，
而译文同位置也带方括号。按**位置**配对，自动挖出 **358 条既成译法，零冲突**。

```
EN  Learn Mic Skill [Stecca Staccato]
ZH  习得音器技能[断奏连击]
                   ↑ 按第 n 个方括号对第 n 个方括号
```

**（2）跨包沿用。**

做 DLC 时，先拿 DLC 的英文去主包已译好的 **1869 条名称 + 8396 条说明文**里查完全相同的，
命中就直接用：名称命中 **40 条**、说明命中 **8 条**（覆盖 66 条实例）。

因为 DLC 里很多怪物本篇就有（`Baal 巴尔`、`Kaiser Dragon 皇帝龙`），
DLC 只是把它们放进了新迷宫。

> **做任何新包，第一步都先跑这个「拿新包的原文去老包的译文里查」**。
> 它不只省工，更重要的是**保证一致性** —— 同一个怪在两个地方叫同一个名字。

## 5.3 译名有疑问时，去翻游戏自己的帮助（stHelp）

这是我觉得最漂亮的一招。

贴图上写 `Support Rate`，我译成「支援率」。用户说：「这个翻译怪怪的，
会不会是粉丝数之类的名词？」

去查 `stHelp.gbin`（游戏内帮助），**日英是逐条对齐的**：

```
stHelp 第 17 行
  JP  支持率
      #FontColor[15]支持率#FontColor[7]は戦闘で勝利した時、またはミッションや…
  EN  Approval Rating
      Your Approval Rating increases after winning battles and clearing Missions…
```

**同一个数值，贴图上叫 `Support Rate`，官方帮助里的英文是 `Approval Rating`、
日文是「支持率」** → 中文就该是「支持率」，不是「支援率」。

用同一招定了 `Turn Back!!`：

```
JP  タクトの追撃でターンバックを発生させるなどして行動順を調整すると良いでしょう。
EN  …you should use Takt's Pursuit to cause Turn Delay and adjust the turn order.
```

`ターンバック` = `Turn Delay` = 数据库里的「行动延迟」，
而且顺带搞清了出现场景（用塔克特的「追击」把敌人行动顺序往后推）。

> **同一个游戏里，日/英双语的平行语料就摆在你面前，这是最硬的实据。**
> 对照办法：`database\database.cl3`（日）和 `database_en\database.cl3`（英）行号一一对应，
> 同一个 `(row, col_offset)` 取两边的值就是逐条对照。
>
> 反面例子：`Wait Damage!!` 在帮助里查无此词，我就**没有硬译**，保持英文等实机确认。
> **猜不出来就别猜** —— 我在这之前凭空猜了个「回合延后!!」，作废重来。

## 5.4 修正层：不改原稿，回填时叠加

术语统一改了 1330 处、地名 170 处、整条重写 1 条、行数收敛 37 条。
这些**都不直接改译稿**，而是写成一个 `fix_zh.py`，回填的时候在内存里叠上去。

好处：原稿始终是「人翻的那一版」，修正是「机器批量改的那一版」，两者分开，
出问题时能分别回退。

**一个细节**：地名匹配要容许被断行切开 —— 译文里可能是「水晶\n洞」，
所以正则要写成 `r'\n?'.join(词)`。而且「水晶洞」要用否定环视 `(?!\n?窟)` 排除「水晶洞窟」。

**还有一条教训**：审计必须审**真正会进包的那一份**（叠加修正之后的），
不是审原稿。我有一轮审的是原稿，漏掉了修正层引入的问题。

## 5.5 排版与角色语气

- 每行 ≤ 22 全角字、每条 ≤ 3 显示行、全屏旁白保持单行
- 角色语气单独立表：响歌用敬语「您」；祢祢结巴怯懦；奏子活泼直接、爱用错成语；
  艾莉亚语句断续、句尾偶带「喵」；桃香暴躁多粗口、忌讳年龄；亚由美冷静毒舌；
  诗织温和带刺、醉后崩坏；塔克特干巴巴的吐槽役；留吉市井腔

语气表的作用是**让批量翻译保持人物一致**。一万多条分 12 批翻，
没有这张表的话，同一个角色在第 3 批和第 9 批会像两个人。

# 六、校验体系：九道闸

这部分是我认为**最应该抄走**的东西。汉化的风险不在「翻错」，
而在「改坏了但不知道」。每一道闸都对应一种具体的翻车方式：

| 闸 | 查什么 | 对应的翻车方式 |
|---|---|---|
| **框宽 / 行数** | 按「同一个显示框」比中英宽度 | 文字溢出框外、被截断 |
| **地名一致** | 17 个地名，数据库 + 剧情，容许断行切开 | 同一个地方两个名字 |
| **跨层术语** | 同形不同义记成**精确条数**（现 157 条） | 批量替换把不该换的换了 |
| **控制码占位符** | `#Icon[..] %s %d` 数量 + 真换行数 | 少一个 `%s` 游戏直接崩 |
| **字形覆盖** | 从**成品包里取字体**查五层文本 | 豆腐块 |
| **贴图溢出** | 改动像素必须落在自己的框里 | 文字串到相邻标签 |
| **擦除自检** | 字芯像素必须 ≥80% 被改掉；重建底板要和框外对得上 | 原文残留、底板被抹糊 |
| **回读比对** | 从**成品包**里解出来重新比 | 打包环节丢东西 |
| **回滚核对** | 改回英文的区域，与原图**逐像素差必须是 0** | 「回滚」其实没滚干净 |

几个设计上的讲究：

**（1）框宽的判据要可证明，不能靠感觉。**

> 英文是游戏自带的，必然放得下 →
> **「中文行数 ≤ 英文行数」且「中文最宽行 ≤ 英文最宽行」⟹ 一定不溢出**

这是个充分条件，不需要知道框到底多宽。粒度必须是「同一个显示框」——
按单条比会漏掉「三条挤在一个框里」的情况。为此我做了字宽表
（CJK 在 sysfont 24px / advfont 35px），31,723 条逐条算。

**（2）字形覆盖要从成品包里取字体。**

不是拿我本地那份改好的字体去查 —— 那查的是「我打算做成什么样」，
不是「实际做成了什么样」。**所有校验都要针对成品，不针对中间产物。**

**（3）同形不同义要记成精确条数，而不是「已检查」。**

`Fan` 可能是「扇形」也可能是「粉丝」，`Seal` 可能是「封印」也可能是「印章」。
这种词有 157 条，我把每一条的裁定写进 `REVIEWED` 列表。
**记成数字**的好处：下次审计如果变成 158 条，我立刻知道有新的进来了要看。

**（4）回滚核对要「逐像素差 = 0」。**

用户后来要求把几处美术字改回英文。「改回去了」这句话不可信，
必须拿成品和原图做逐像素比对，差异必须是**字面意义上的 0**。

# 七、交付工程：这部分的难度超出我预期

## 7.1 400MB 的墙

`Game3.bra` 740MB、`Game4.bra` 721MB，我这边的传输预算是**单次约 50 秒、400MB 上限**，
根本拿不到手。但标题画面、迷宫横幅、地图图例都在这些大包里。

两把钥匙：

**（1）只读索引，不读整包。**

索引在文件尾部 → `seek` 过去读那几十 KB 就行。写了个 PowerShell 脚本在用户机器上跑，
列出成员名、按名字解压出指定的那几个成员发回来。**721MB 的包，只传了 122KB。**

**（2）按成员名寻址的原地补丁。**

我这边只产出「新的成员内容」，**偏移让 Windows 侧的脚本自己读索引算**。
这样我根本不需要拿到整个包。

## 7.2 三代补丁格式的演进

| | 寻址方式 | 问题 |
|---|---|---|
| **OQPATCH1** | 写死字节偏移 | 必须先拿到整个包才能生成；换个版本就废了 |
| **OQPATCH2** | **按成员名** | 新压缩块必须塞得回原槽位 |
| **OQPATCH3** | 按成员名 + **塞不下就追加到文件末尾** | —— |

OQPATCH2 的「必须塞回原槽位」是个真实的约束。为了多挤出几个字节，
压缩换成了 **zopfli** 而不是 `zlib -9` —— 每个成员多省约 1500 字节，
`menu_Quit` 就是靠这个才塞进去的（`zlib -9` 差 103 字节）。

**但字体塞不回去**（advfont 15.1MB → 33.5MB）。于是有了 OQPATCH3，改动只有一条：

```
塞不下 → 追加到文件末尾，然后改索引里的 off 字段
```

索引项布局：`<IIIIHHI>` = csz@+8、usz@+12、nl@+16、flg@+18、**off@+20**。
BRA 的索引本来就在文件尾部，往后追加不影响任何东西。
代价是旧槽位变成死区（System.bra 打完大 10MB），无害。

## 7.3 为什么最终发的是**差分补丁**，不是整包替换

这是个定性判断，不是技术问题：

> **整包分发 = 把游戏本体数据一起发出去。**
> 改成只含改动成员的差分补丁，接收方必须自己有正版游戏。

顺带发现，差分反而**小得多**：System.bra 110 个成员里只有 **22 个**被改过，
压缩后 11.8MB（其中 10MB 是中文字体），加上 DLC 34KB、Game1 347KB、Game4 471KB，
整包 **12.5MB**。而整包替换要 127MB。

## 7.4 补丁必须自带的四件事

1. **原版校验**：每条记录里存**原始成员的 MD5**，应用前逐个核对。
   对不上 → **一个字节都不写**，并提示「在 Steam 里验证游戏文件完整性」。
   这防住了「在别人改过的包上打补丁」这种最容易炸的情况。
2. **幂等**：已经是新内容的成员跳过，全部跳过就报「已经打过了」。
3. **写后回读校验**：写完再逐个解压出来对 MD5，不过就**自动回滚**。
4. **撤销文件**：只记录被覆写的那些区段 + 原文件长度（回滚要 `truncate`）。
   卸载后必须**逐字节等于原版**。

## 7.5 Windows 侧的编码陷阱（这几条纯属经验，没有道理可讲）

- **无 BOM 的 `.ps1` 必须是纯 ASCII** —— PowerShell 5.1 按系统 ANSI 代码页（GBK）读它。
  要在 `.ps1` 里写中文，就存成 **UTF-8 + BOM**。
- **`.bat` 用 GBK + CRLF**，而且**生成后要逐字节扫一遍**：
  GBK 汉字的尾字节可能撞上 cmd 元字符（`| ^ \ " & < > % ( )`），
  一撞整行语义就变了。我的生成脚本里有这个断言。
- 改 `.bat` 要**连 CRLF 一起保住**，重新生成整份最稳。

## 7.6 最后：装一个真的 PowerShell 来跑

我一开始只写了个 Python 孪生脚本验算法。**这不够。**
后来在容器里装了真的 PowerShell 7：

```
curl -sSL https://github.com/PowerShell/PowerShell/releases/download/v7.4.6/powershell-7.4.6-linux-x64.tar.gz
```

然后跑完整的七项验证：

| 验证 | 结果 |
|---|---|
| 重建原版包 → 打补丁 → 与成品逐成员比 | System 110 个成员**不一致 0**；DLC 305 个**不一致 0** |
| Game1 原版 → 打补丁 | 改动 35 个成员，回读校验全过 |
| 重复打 | `already patched`，幂等 |
| 卸载回滚 | 三个包 MD5 **逐字节等于原版** |
| 故意破坏一个被覆盖的成员 | 正确拒绝，**一个字节都没写** |
| 从 zip 解压出来重跑 | 全绿 |

> **要交给别人用、还要让别人转发的东西，不能只靠「算法等价」的验证。**
> 目标语言的运行时一定要真跑。

# 八、DRM 这堵墙：什么时候该停

exe 里还有 79 条会露脸的英文（设置项、存档对话框、DLC 礼包说明、五句教程提示）。

这个 exe 带 **SteamStub** 外壳：多一个 `.bind` 段，`.text` 在盘上是加密的。
两次试装都报 `Application load error 3:0000065432`：

- 第一次改了指针 + 字符串；
- 第二次缩到**只改 `.rdata` 里 822 字节**、别处一字节不动 —— 还是同一个错。

结论：**SteamStub 的校验范围包含 `.rdata`，这个 exe 一个字节都改不得。**

指针表虽然在 `.data`（通常不在校验范围里），理论上可以加一个新段放中文字符串、
把指针指过去。**但那是在绕过防篡改校验本身，这条线我不做。**

> 技术上「能不能」和「该不该」是两个问题。
> 这里我的判断是：汉化游戏数据是改自己买的游戏的资源文件；
> 而绕开反篡改校验是另一回事。所以这 79 条就保持英文，
> 在说明里写清楚原因，让用户知道这不是漏做。
>
> 做这类项目，**提前把自己的边界说清楚**，比事后纠结省事。

# 九、和「用户」协作的部分（其实这是最影响效率的一环）

19 轮里有大量来回。回头看，效率高低几乎全取决于反馈的质量：

**（1）截图比文字描述强一个量级。**

用户发的那张 GET ITEM 截图，一张图里同时有英文的 `Vitamin Supplement` 和
中文的「迷彩模糊」—— 这两个名字在数据里是**同一张表同一个字段**。
这一张图直接把「是不是包没生效」这个方向彻底排除，把问题定性成「横幅另有取名路径」。
在那之前我已经查了两轮、写了一份结论错误的报告。

**（2）改前改后对比图，能省好几轮。**

每处改动都出一张对比图（原版 / 上一轮 / 这一轮），用户一眼确认。
指令表字号那次我出了三版对比，用户立刻指出我理解反了。

**（3)「不确定的结论要重测」这条规矩救了我。**

我有三份结论是错的（「截图可能是旧的」、「支援率」、「状态异常改错了框」），
都是因为被要求重测才发现。**逆向工程里，「查不到」和「不存在」差得很远。**

**（4）每轮写全新报告，不要在旧报告上打补丁。**

一开始我想省事，在旧报告上改。结果是没人知道哪一版是最新的。
改成每轮一份新报告 + 一份始终最新的交接文档，清楚多了。

# 十、如果你要从头做另一个游戏，我会建议这个顺序

```
1. 拆容器，并立刻写「原样重打包 → 逐成员比对」的自检         ← 不产出东西，但是底线
2. 列出所有成员名，画出数据地图（哪些是文本、贴图、字体）
3. 把所有贴图解出来拼 contact sheet，肉眼扫一遍             ← 十分钟，能省好几轮
4. 挑最小的一块（菜单几百条）+ 字体，跑通「改→打包→实机」全链路  ← 第 1 轮就要看到中文
5. 逐个格式逆向，每张表先过「空重建闸」，过不了的走窄路
6. 先跑「白捡译文」（跨包沿用 + 括号配对），再翻剩下的
7. 边翻边建校验闸，出包前全绿才交
8. 贴图放后面做（最费时），先 overview 再逐块
9. 交付走差分补丁，自带原版校验 + 回读 + 回滚，并用目标平台真跑
10. exe 那种带反篡改的，早点验、早点放弃、写清楚原因
``` 

**最后三句总结**：

1. **每一道自检都对应一种具体的翻车方式。** 想不出来它防的是什么，这道闸就是摆设。
2. **「我理解得不够」和「我完不成」是两件事。** 空重建闸的价值就是把它们分开。
3. **搜不到 ≠ 不存在。** 先问「我是不是只查了我以为存在的那一种存法」。
